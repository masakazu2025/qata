# 現場の知識の書き方

qata は公開するリポジトリです。現場の知識は公開しません（D28）。

| 区分 | 例 | 文書には |
| --- | --- | --- |
| 自動化の一般論 | Windows アプリ・Web の自動化、文字の読み方、スクショの撮り方 | 積極的に書く |
| 業務アプリ全般に共通すること | 起動し直せない常駐アプリ、途中で止まったときの立て直し、複数の画面にまたがる全画面のアプリ、古い Windows アプリ | 一般化して、「こういうユースケースも想定する」として書く |
| 特定の業務（POS など）に固有のこと | 実際の操作・画面・業務の手順 | 書かない。人がチャットで話しても残さない |

- 迷ったら、「この文から、特定の業務や製品が分かるか」で決める。分かるなら書かない。
- 分かるかどうか判断がつかなければ、人に聞く。自分で判断しきらない。
- 業務の知識は、セキュリティに関わるものとして慎重に扱う。一つずつは一般的でも、組み合わせると特定の業務や製品が分かることがあるので、性質を並べるときも気をつける。
- 人の発言から知識を文書に書くときは、一般化してから書く。
- 知識の置き場所は親の `docs/knowledge/`（用語集・業務アプリの性質・自動化で困ること・想定するユースケース）。decisions や ideas に知識が出てきたら、knowledge に書いてリンクで指す。
- 文書・コード・画面の言葉は、用語集（`docs/knowledge/glossary.md`）に合わせる。新しい言葉を使い始めたら、用語集に足す。
