# Git

GitHub Flow で進める。`main` と作業用のブランチだけを使い、`main` には pull request で入れる。

## ブランチ

- `main` に直接コミットしない。issue ごとにブランチを切る。一つの issue は一つのセッションで終える大きさにするので（`issues.md`）、基本は 1 issue・1 セッション・1 ブランチ。
- 名前は `<種類>/<内容>`。種類は `feature`（作る・足す）、`fix`（直す）、`docs`（文書・ルールだけ）。内容は英小文字とハイフン（例：`feature/contracts`）。
- 一つのブランチで、二つの issue をやらない。

## コミット

- 関門を通った状態でコミットする。1 セッションに少なくとも 1 コミット。
- メッセージは日本語で、何をしたかを一行で書く（例：「契約の案を作る」）。要るときは、空行のあとに理由を書く。
- まとまりごとに分ける。一つのコミットに、関係のない変更を混ぜない。

## main に入れる

- issue が終わったら、ブランチを push し、`main` への pull request を作る。
- `main` に入れるのは、関門を通ったものだけ。
- マージは AI がしてよい（中身は人がセッションの中で見ているので、pull request は記録として残す）。マージはマージコミットで行い、コミットの分け方を残す。マージしたらブランチを消す。
- これ以外の push（`main` への直接の push、強制の push など）はしない。

## リポジトリをまたぐとき

正（契約など）を持つリポジトリと、それを読むリポジトリの決まり。読む側は、読む正の版を自分で持つ（版の固定）。

- **どのリポジトリの `main` も、いつも関門を通る状態に保つ。** 決まりどおりの順でも、ほかのリポジトリの `main` を落としてよいことにはならない。
- 正の pull request は、読む側を待たずにマージしてよい。読む側は、自分の pull request で版を上げるまで、前の版を読み続ける。
- 読む側は、版を上げる pull request で、正から生成したもの・写したものを作り直し、関門を通してからマージする。
- ブランチはリポジトリごとに一つ切る。一つのリポジトリで二つの issue をやらない決まりは、そのまま守る。
- **版の固定がまだ入っていない読む側では**、正を先にマージすると読む側の `main` が落ちるとき（生成した型が合わなくなる、例が変わるなど）は、マージせずに止めて人に聞く。

### 版の上げ方

正を変える pull request では、同じ pull request の中で、正の版を上げる。

**版は、点で区切った三つの数（例：`1.4.2`）。** 左から、壊した・足した・説明だけを直した、を表す。広く使われているセマンティック バージョニングと同じ考え方。

```
  1  .  4  .  2
  │     │     └ 三つ目：説明の文・例だけを直した
  │     └────── 二つ目：足した（前の形はそのまま使える）
  └──────────── 一つ目：壊した（前の形が使えなくなった）
```

- どの数を上げるかは、読む側から見た変わり方で決める（下の表）。
- 一つを上げたら、それより右の数は 0 に戻す。だから `1.4.2` で足すと `1.4.3` ではなく `1.5.0` になる。
- 読む側は、どの数が上がったかだけで、どれくらい急いで追いつくかが分かる。一つ目なら前の形が使えなくなった、二つ目なら新しいものが使える、三つ目なら形は何も変わっていない。

| 変わり方 | 上げる数 | いまの版が `1.4.2` なら |
| --- | --- | --- |
| 壊す：項目や道を消す・名前を変える・必須にする・制約を狭める・意味を変える | 一つ目 | `2.0.0` |
| 足す：任意の項目・引数・道・値を足す、制約を広げる | 二つ目 | `1.5.0` |
| 説明の文・例だけ | 三つ目 | `1.4.3` |

続けて変えると、次のように進む。

| 変更 | 変わり方 | 版 |
| --- | --- | --- |
| 最初の版を付ける | — | `1.0.0` |
| 説明の文を直す | 説明だけ | `1.0.1` |
| 任意の項目を足す | 足す | `1.1.0` |
| 例に、その項目を入れる | 説明・例だけ | `1.1.1` |
| 古い項目を消す | 壊す | `2.0.0` |

読む側が `1.0.0` を読んでいる間に正が `1.1.0` になっても、読む側は落ちない。読む側が自分の pull request で `1.1.0` に上げたときに、新しい項目を使えるようになる。

- 迷ったら、大きいほうを上げる。
- 正の側は、マージしたら版のタグを付け、変更の記録に「版・何を変えたか・どの変わり方か・読む側がすること」を書く。
- **壊す変更は、なるべく三段に分ける。** 新しい形を足す（二つ目）→ 読む側がすべて新しい形に移る → 古い形を消す（一つ目）。消す段は、すべての読む側が移ってから入れる。
- 一つ目か二つ目を上げたら、正の pull request の説明に、上げる必要のある読む側を書き、読む側ごとに issue を立てる（その変更を使う issue がすでにあれば、それでよい）。三つ目だけなら issue は立てず、その読む側を次に触るときに上げる。
- 読む側の版を上げる pull request の説明には、上げる前と後の版と、記録のどの項目に対応したかを書く。
- 読む側が最新から遅れてよいのは、周回の中だけ。周回の振り返りの前に、すべての読む側を最新の版に上げる。
- 読む側の CI は、読む版が最新より古いとき、警告を出す（関門は落とさない）。
- 読む側どうしが使い合うとき（ある読む側のテストが、別の読む側を動かすなど）は、使われる側を先に上げる。
