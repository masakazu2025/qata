# Git

GitHub Flow で進める。`main` と作業用のブランチだけを使い、`main` には pull request で入れる。

## ブランチ

- `main` に直接コミットしない。issue ごとにブランチを切る。一つの issue は一つのセッションで終える大きさにするので（`issues.md`）、基本は 1 issue・1 セッション・1 ブランチ。
- 名前は `<種類>/<内容>`。種類は `feature`（作る・足す）、`fix`（直す）、`docs`（文書・ルールだけ）。内容は英小文字とハイフン（例：`feature/contracts`）。
- 一つのブランチで、二つの issue をやらない。

## コミット

- 関門を通った状態でコミットする。1 セッションに少なくとも 1 コミット。
- メッセージは日本語で、何をしたかを一行で書く（例：「契約の案を作る」）。要るときは、空行のあとに理由を書く。
- まとまりごとに分ける。一つのコミットに、関係のない変更を混ぜない。

## main に入れる

- issue が終わったら、ブランチを push し、`main` への pull request を作る。
- `main` に入れるのは、関門を通ったものだけ。
- マージは AI がしてよい（中身は人がセッションの中で見ているので、pull request は記録として残す）。マージはマージコミットで行い、コミットの分け方を残す。マージしたらブランチを消す。
- これ以外の push（`main` への直接の push、強制の push など）はしない。

## リポジトリをまたぐとき

一つの issue で、正（契約など）を持つリポジトリと、それを読むリポジトリの両方に pull request が要るときの決まり（暫定）。

- 正を持つほうを先にマージする。そのあと読む側の CI を回し直し、通ってから読む側をマージする。読む側の CI は正の `main` を読むので、逆の順では通らない。
- それぞれの pull request の説明に、相手の pull request とマージの順番を書く。
- 正に合わせて作り直すだけのような小さな追従なら、読む側のリポジトリの issue は立てない。正の側の issue を指す pull request（`Refs owner/repo#番号`）だけでよい。
- ブランチはリポジトリごとに一つ切る。一つのリポジトリで二つの issue をやらない決まりは、そのまま守る。
