# 振り返り

周回ごとの振り返りを置きます。新しい周回を上に足します。記録する項目は [process.md](process.md) の「振り返り」に従います。

## 数え方

* **時間**：Claude Code のセッションの記録の、最初と最後の時刻の差。セッションの間の休みは入れない。管理の拡張の 1 周目からは、セッションの中の 20 分を超える空き（人の返事待ちや席を外した間）も除く。

* **人の発言**：セッションの記録から、人が打った発言を抜き出し、AI が次の 4 つに分けた。分け方は AI の判断で、目安です。

  * **直した**：AI の進め方・案・ルールを、人が直した。**仕組みが育ったかの指標は、これが減っていくこと。**

  * **決めた**：人が決めるもの（目的・スコープ・対象の業務アプリの前提など）に答えた。AI に聞かれて答えたものも含む。

  * **聞いた**：人が理解するために聞いた（技術の説明など）。

  * **定型**：セッションの開始（「つぎ」）、マージの許可、GitHub のリポジトリの URL、あいさつ。

* 途中で止めた（中断）だけのものは数えない。

* AI の選ぶ形の質問への答えも、人の発言として数える。

### 気づき（AI）

1. **決まりどおりに進めて、`main`** **を落とした。** 「またぐときは正を先にマージする」の決まり（暫定）は、マージの順を決めていたが、その間に読む側の `main` が落ちることを止めていなかった。設計の「正から作ったもの」の基準も、作り直すものを直すとしか書いていなかった。足すだけの変更でも子が落ちたのは、子が親の `main` を版を固定せずに読み、生成した型が契約とまったく同じかまで見ているため。

   * **扱い：** 三つのやり方を比べ、人が版の固定に決めた（2026-11-18、D52）。後方互換の変更は、子が落ちない作りがあって初めて効く。まとめ用のブランチは、`main` に入れる瞬間に数分落ち、足すだけの小さな変更でも毎回ブランチが 3 本要る。版の固定なら、親をマージしても子は前の版を読み続け、子が自分の pull request で追いつく。git.md の「リポジトリをまたぐとき」を版の固定の形に書き直し、版の上げ方を決まりにした（人から「版を更新するルールだけは、しっかり」）。design の基準にも足した。仕組みを入れるのは [qata#69](https://github.com/masakazu2025/qata/issues/69)（runner・server・web の sub-issue 付き）。入るまでは「落ちるならマージせずに止めて人に聞く」で守る。困ったら直す。

2. **人に動作を見せることが、終わりの条件に入っていなかった（2 回）。** web（4）で、AI は e2e のスクショを人に PR へ貼ってもらおうとし、人から「動作を見せて」「デモ版にも試せるデータを」と頼まれた。土台の入れ替えの web のセッション（11-17）でも「実際に画面を見たい」と頼まれていた。メモリには「動作は画面で見せる」があったが、スキルになかった。

   * **扱い：** requirements の観点に「人が触れるか」を足した。画面が変わる issue では、手元で動かして人に見せることと、デモ版で試せるデータを、終わりの条件に入れる。

3. **`docs/decisions.md`** **に項目を足したとき、すぐ下の項目の見出しが消えた（2 回、qata-web の W8・W9）。** 文書を置き換える一回きりのスクリプトの誤りで、prettier は文の形しか見ないので通った。2 回とも reviewer が見つけた。

   * **扱い：** implement の手順に「文書を書き換えたら、差分で消えた行を見る」を足した。見出しの番号が抜けなく並ぶことを確かめる検査は、文書の検査をまとめて入れるときに考える（[ideas.md](ideas.md) に置いた）。

4. **「直した」は減らず、部品のセッションに移った（4 回 → 5 回）。** 前の周回までは、直しは文書と計画の段に集まり、部品の段は 0 回だった。今回の 5 回は、どちらもコードの中身ではなく、issue をまたぐ進め方（マージの順）と、人との受け渡し（動作を見せる）だった。工程のスキルは、一つの issue の中のことしか見ていない。

   * **扱い：** 1 と 2 で、それぞれスキルに落とした。周回をまたぐことは、次の工程ごとの確かめ（[qata#59](https://github.com/masakazu2025/qata/issues/59)）で、確かめるエージェントの観点に入れるかを考える。

5. **部品の三つは 76 分で終わり、server は口出しがなかった。** 土台を先に入れ替えた（D43・D49）ので、タグの表の変更は Alembic の移行一本で済み、web も TanStack Query の上に足すだけだった。reviewer は三つとも指摘を出し、すべてその場で直した。

   * **扱い：** 何もしない。土台を先に固める順番が効いたことの記録として残す。

* **時間から、セッションの中の 20 分を超える空きを除く。** 2 周目の振り返りで、人から「出かけることもあるので、待ち時間を含める意味があるのか疑問」と言われた。今回の 1 のように、質問への答えを一晩待つと、分の数が意味を持たなくなるため。空きを入れた分も表に残し、比べられるようにした。

### 人から

* 技術的な追加が多く、知見がないのでベストプラクティスに任せるしかなかったため、レビュアーとして機能をあまりしなかった

* ドキュメントが徐々に乱雑になってきているので、いずれはフォーマットを整えて、フックを元に更新する仕組みにできるものはしたほうがよい

* 画面を見せる必要がある、と自律的に改善してくれたのは◎

* どのmainも落とさない、は、後方互換の変更 などを考慮すると、少し過剰だと思う（人間の知識不足が原因）

* タグの状態など、確認するには登録画面やPOSTMANがないと、十分にチェックができないため、今回は素通りが多かった。

  環境構築をするか、次の登録画面でもって、タグの動作確認を行うべき

* タグの絞り込みは、当然今回が単なる機能実装だった為だと思うが、デザイン・置き場所に難があるため、今後機能を追加していく過程で、検索の仕方を考慮する。

  * テストケース画面で、タグをクリックすると、タグでの絞り込み一覧に移行する（検索画面が実装されてることが前提）

  * タグは、テスト一覧で選択すると言うよりは、検索画面で入力する方が、自然だと思われる

* レビューの内容が、技術的にわかっている人というか、文脈がわかっている人になってきていて、読んでもわからないことが多くなってきた。特に、提案の内容が、間を省略しすぎていて、読んでもわからないことが多い
