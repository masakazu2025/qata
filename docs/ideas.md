# ideas

次回以降の改善案を置きます。作業の途中で出てきた「別の直したいもの」「あとで考えたいこと」もここに逃がします。今のスコープには入れず、次の周回の計画のときに検討します。

部品のリポジトリから、全体に関わる改善案を上げるときもここに書きます（どこから、を添える）。

## 次の周回で、先に取り組むもの（人）

- **親と子の関係を、ルールとして書いていく。** いまは子が親のルールをすべて読み込んでいる（D24）が、それはよい形ではない。子が親から何を受け取り、何を自分で持つのかを、ルールとして決める。
- **子が契約を親から写して持つ。** 子は別のリポジトリなので、親の契約を写して使う形でもよい（アイディアの段階）。いまは、子が隣に並べた親（`../qata/`）を読んでいる。
- **CI と、マージ前の AI のレビューを入れる。** CI は GitHub Actions とブランチの保護で、AI のマージは `gh pr merge --auto` だけにする。レビューは別の文脈の `/code-review` で行い、指摘は PR のコメントに残す。CI だけではテストを書いた AI が採点もしているので弱い。それまでは、マージの前に人が一言出す。レビューの観点は、気づいたものから少しずつスキルやチェックリストに切り出す。最初の候補は次の二つ。
  - FastAPI の型の名前が、契約の型を上書きしないか（qata-server の S6 で見つけた）。
  - 関門のテストが、わざと壊したコードを本当に捕まえるか（その場で壊して確かめる。qata-server の MCP で試した）。
- **親を相対のパス（`../qata/`）で指すのをやめる。** 公開してポートフォリオにも載せるので、リポジトリ単体で読めて、動く形がよい。上の二つとまとめて直す。

## そのほか

- コードの書き方を縛るもの（最初の周回の振り返りから、人）。人はコードの中身を見ないので、ここで確かさを押さえる（D29）。
  - コーディング規約と、優先して採用するデザインパターン。規約は、関門で確かめられるものから決める。
  - フォルダの雛形。先に設計せず、いまある部品（server・runner・web）で重なっているもの（pyproject・ruff・import-linter・.gitattributes など）から抜き出す。
  - 技術のレビュー。精度は、答えの分かっている不具合をわざと入れて、見つけるかで確かめる（人が全部を読まずに済む）。
- 関門をすり抜けて、あとで見つかった問題を数える（最初の周回の振り返りから）。「直した」回数だけでは、人が見ていないから少ないのかが分からない。偽物を本物に置き換える周回から数える。

- ルールとスキルが食い違っていないかを、レビューの観点にする（最初の周回の振り返りから）。D21 でルールを直したのに session-end の手順が古いままで、同じ指摘が二度出た（D25）。
- 技術の説明は、結論と例を先に出す（最初の周回の振り返りから）。JSON Schema と pydantic の違いの説明に 14 往復かかった。ルールにするかは次の周回で決める。
- 振り返りの数字を集めるスクリプト（セッションの記録から、時刻と人の発言を抜き出す）。最初の周回は、その場で書いて使い捨てた。

- タスク管理ツール（Linear など）と共存させる。いまは各リポジトリの `docs/tasks.md` で持っているが、部品のリポジトリが増えて、リポジトリをまたぐ段取りが出てきたら、一か所で優先順を見られるツールのほうがよい。
- 改行コードをそろえる（`.gitattributes`）。いまは Windows で git が LF を CRLF に変えると警告を出す。
- 部品の辞書（D14）の改良。辞書の作り方や、何かを読み込んで辞書を更新する仕組みは構想がいくつかあり、いまは名前をアクションに変える最低限の形にしている。
- 文字の読み方を足す（D17）。OCR（スクショから読む）や、古いアプリ向けの手段（Win32 のウィンドウの文字を読むなど）。runner への命令の `source.method` に種類を足す。
- 修飾キーとの同時押し（Ctrl+C など）。同時押しを判定する業務アプリもあるので、いずれ要る。PoC の電卓では要らないので、キーは 1 文字か名前付きのキーだけにした（D13）。
- テストの前後で、対象の状態を立て直す仕組み（D16）。起動し直せない業務アプリでは、止まった状態に応じて自動で操作する必要がある。リグレッションテストの実装のときに最初に取り組むところ（人）。
  - 止まった場所が特定できるなら、そこから処理を取り消して終わらせる。
  - 取り消せないところまで進んでいるなら、処理を最後まで進めて終わらせる。
  - それでも無理なら、ログを採ってから再起動する。
  - 対象が落ちたら、それを検知してログを採る。
- openapi.yaml の 409 の説明を、server の実際に合わせる（qata-server から。REST を作っていて見つかった）。`runTestcase` の 409 は「人の確認待ち」だけと書いてあるが、登録のあとで部品の辞書が変わったとき（`testcase_out_of_date`）も 409 になる（qata-server の S5）。形は変わらないので、いまの作業は止まらない。
