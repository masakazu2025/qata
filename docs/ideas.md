## デモが終わってから、本格的に取り組むもの（人）

次の周回では、下のものは最低限だけやり、デモの完了（本物の電卓）を先にする（D30）。最低限の中身は当時の tasks.md に置いた。

- **親と子の関係を、ルールとして書いていく。** いまは子が親のルールをすべて読み込んでいる（D24）が、それはよい形ではない。子が親から何を受け取り、何を自分で持つのかを、ルールとして決める。
- **子が契約を親から写して持つ。** 子は別のリポジトリなので、親の契約を写して使う形でもよい（アイディアの段階）。いまは、子が隣に並べた親（`../qata/`）を読んでいる。
- **CI と、マージ前の AI のレビューを入れる。** CI は GitHub Actions とブランチの保護で、AI のマージは `gh pr merge --auto` だけにする。レビューは別の文脈の `/code-review` で行い、指摘は PR のコメントに残す。CI だけではテストを書いた AI が採点もしているので弱い。それまでは、マージの前に人が一言出す。レビューの観点は、気づいたものから少しずつスキルやチェックリストに切り出す。最初の候補は次の二つ。
  - FastAPI の型の名前が、契約の型を上書きしないか（qata-server の S6 で見つけた）。
  - 関門のテストが、わざと壊したコードを本当に捕まえるか（その場で壊して確かめる。qata-server の MCP で試した）。
- **親を相対のパス（`../qata/`）で指すのをやめる。** 公開してポートフォリオにも載せるので、リポジトリ単体で読めて、動く形がよい。上の二つとまとめて直す。
  - ルールとスキルをプラグインで配る方法は調べた（[qata#31](https://github.com/masakazu2025/qata/issues/31) のコメント）。スキルは配れるが、ルールは配れない。作業が大きいので、いまはやらない（D37）。
  - 最低限は入れた（D33）。CI で親のリポジトリを丸ごと取ってきて、`QATA_PARENT_DIR` で指している。デモのあとで、子が使うもの（契約など）だけを写して持つ形にし、要らないものを外していく。
- **CI の本格化。** 最低限（いまのテストを回して、通らないとマージできない）は入れた（D33）。AI のレビューと `gh pr merge --auto` は、デモのあとに入れる。ほかに、CI で入れてから気づいたもの。
  - 親の契約を変える pull request では、子の CI が回らない（子は親の main を読む）。契約の変更が子を壊しても、子の次の pull request まで気づかない。
  - 部品をまたぐ変更は、server・runner を先にマージしないと web の e2e が通らない（e2e は隣の main を使う）。いまは順番で済ませている。

## そのほか

- コードの書き方を縛るもの（最初の周回の振り返りから、人）。人はコードの中身を見ないので、ここで確かさを押さえる（D29）。
  - コーディング規約と、優先して採用するデザインパターン。規約は、関門で確かめられるものから決める。
  - フォルダの雛形。先に設計せず、いまある部品（server・runner・web）で重なっているもの（pyproject・ruff・import-linter・.gitattributes など）から抜き出す。
  - 技術のレビュー。精度は、答えの分かっている不具合をわざと入れて、見つけるかで確かめる（人が全部を読まずに済む）。
- 関門をすり抜けて、あとで見つかった問題を数える（最初の周回の振り返りから）。「直した」回数だけでは、人が見ていないから少ないのかが分からない。偽物を本物に置き換える周回から数える。

- ルールとスキルが食い違っていないかを、レビューの観点にする（最初の周回の振り返りから）。D21 でルールを直したのに session-end の手順が古いままで、同じ指摘が二度出た（D25）。
- 技術の説明は、結論と例を先に出す（最初の周回の振り返りから）。JSON Schema と pydantic の違いの説明に 14 往復かかった。ルールにするかは次の周回で決める。
- 振り返りの数字を集めるスクリプト（セッションの記録から、時刻と人の発言を抜き出す）。最初の周回は、その場で書いて使い捨てた。

- 改行コードをそろえる（`.gitattributes`）。いまは Windows で git が LF を CRLF に変えると警告を出す。
- 部品の辞書（D14）の改良。辞書の作り方や、何かを読み込んで辞書を更新する仕組みは構想がいくつかあり、いまは名前をアクションに変える最低限の形にしている。画面の文字列から、ボタンの位置を探す案もある（機能のブレスト、qata#34）。
- 文字の読み方を足す（D17）。OCR（スクショから読む）や、古いアプリ向けの手段。runner への命令の `source.method` に種類を足す。なぜ要るかは [app-traits.md](knowledge/app-traits.md)。文字の一致だけでなく、画面に何が表示されているかをチェックする確認事項も、ここから広げる（機能のブレスト、qata#34）。
- 修飾キーとの同時押し（Ctrl+C など）。PoC の電卓では要らないので、キーは 1 文字か名前付きのキーだけにした（D13）。なぜ要るかは [app-traits.md](knowledge/app-traits.md)。
- テストの前後で、対象の状態を立て直す仕組み（D16）。リグレッションテストの実装のときに最初に取り組むところ（人）。立て直しの流れ（3 段・始める前の状態）は [automation-pitfalls.md](knowledge/automation-pitfalls.md)。判断（その場で回避する）は外の AI に置き、qata は取り消しシナリオを流すことと、始める前の状態に戻ったかを確かめることを持つ（D39）。

- AI が実行の結果のスクショを見られるようにする（2026-11-08、デモで AI から出た指摘）。指摘は「run_testcase の結果にスクショの URL を入れる」だったが、URL では MCP のクライアントに画像が見えないことが多く、1 回の実行で 6 枚を毎回返すのも重い。スクショ一枚を MCP の画像で返す道具（`get_screenshot`）を足し、失敗したときなど要るときだけ取りに行く形がよい（AI の考え）。
- 人に承認を頼む流れを短くする（2026-11-08、デモで AI から出た指摘）。指摘は「承認待ちで止まったときのエラーに、web の承認画面へのリンクを入れる」。登録した時点の結果に承認画面の URL を入れれば、実行して止まる前に頼める（AI の考え）。server に web の場所の設定（`QATA_WEB_URL` など）が要り、web にテストケースごとの URL があるかは未確認。

## 機能のブレストから（2026-11-14、[qata#34](https://github.com/masakazu2025/qata/issues/34)）

qata の範囲と、本体・切り出す道具・周辺の分け方は D39。全体の図は [vision.md](vision.md)。次に作る周回の計画のときに検討する。

### 本体：テストケースの管理

契約（テストケースの形式）が変わるので、まとめて検討する。

- **タグ。** 機能・元の設計書・対象アプリの版を持ち、「設計書 A に紐づき、v2.1 以上で有効」のように絞り込める。
- **有効な版は範囲で持つ。** 1 つの値ではなく、「この版から有効（必要ならこの版まで）」。
- **クローン。** 手順を流用して、確認事項だけ変える。元のテストを記録し、タグを引き継ぐ。元のテストも残す（古い版の確認で使う）。

### 切り出す道具（qata の外の、独立したモジュール）

runner に頼らずに作り、端末で単独に動かすか runner に組み込むかは、現場の制約が見えてから決める（D39）。

- 設定（設定のファイルや、許可されたレジストリ）を変えて、アプリを再起動する。
- 設定が正しいかを確かめる。自動化とは別の用途もある。
- ログを集める。不具合の現象を書くのは外の AI で、道具は集めるだけ。「ログにこの行が出るまで待つ」も、テストを二つに分け、その間で AI がこの道具で確かめる形から始める。

### 周辺

- 外部の相手の代わりをするシミュレータの起動と、設定値の切り替え。
